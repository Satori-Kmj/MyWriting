# MyWriting

MyWriting 是一套运行在 DeepSeek Harness（DSH）中的小说写作工作流。仓库保存工作流、插件源码、测试和无私人信息的示例；人物卡、正文、状态和本机配置应只留在本地。

## 目录布局

- `.dsh/skills/`：写作流程的各阶段说明。
- `plugin/src/`：DSH 工具与写入保护插件。
- `plugin/tests/`：工作流回归测试。
- `config/`：本地写作系统。
- `reference/characters/`：稳定人物档案。
- `state/rag/`：持续人物状态。
- `input/`、`work/`、`output/`、`state/`、`history/`：运行时输入、中间产物、输出、状态和不可变历史。

## 功能概览
- 分阶段写作
- 大纲扩展
- 正文生成
- 候选修改
- 用户确认后才提交
- 人物持续状态
- History / checkpoint
- 写入保护

## 建立本地私人配置

示例文件可以提交，但不要把私人内容直接写入示例。

1. 将 `config/writing-system EXAMPLE.md` 复制为 `config/writing-system.md`，再填写正式写作要求。
2. 将 `reference/characters/EXAMPLE 人物档案.md` 复制为 `reference/characters/<人物名>.md`。
3. 将 `state/rag/EXAMPLE状态文件.md` 复制为 `state/rag/<人物名>状态.md`。

`<人物名>状态.md` 中的七个二级标题均须保留，标题名称必须与示例完全一致。每条实际状态使用 `- 内容` 格式；没有内容的章节可以为空。

上述正式私人文件和所有运行时产物已由 `.gitignore` 排除。`.gitkeep` 只用于让 Git 保存空目录，不属于故事数据。

## DSH 与插件配置

当前依赖和脚本假定目录布局如下：

```text
DSH/
├── deepseek-harness/
└── MyWriting/
```

将 `plugin/cordis.patch.template.yml` 复制为 `plugin/cordis.patch.yml`，并把 `__MYWRITING_SRC_URL__` 替换为当前机器上 `plugin/src` 的 file URL。实际 `cordis.patch.yml` 包含本机路径，因此不会被 Git 提交。

## 验证

在 `plugin` 目录运行：

```powershell
pnpm run typecheck
pnpm test
```

提交前可使用以下命令确认待提交文件：

```powershell
git status --short

```

不要使用 `git add -f` 强制添加被忽略的私人文件。


#### 功能概览

MyWriting 的目标不是让模型一次性“根据大纲写一篇小说”，而是将小说创作拆分为可检查、可修改、可持续推进的工作流，让用户保留对剧情和最终结果的控制。

### 分阶段写作流程

一次完整的创作会依次经过：

```text
用户大纲
   ↓
粗纲
   ↓
扩写大纲
   ↓
正文
   ↓
用户确认
   ↓
采用并更新状态 / History
```

不同阶段承担不同任务：前期负责整理剧情结构和补充必要细节，正文阶段专注于实际创作，而人物状态和历史记录只会在用户确认采用之后写入。

这样可以避免一次生成同时承担“理解剧情、规划结构、创作正文、更新记忆”等过多任务，也允许用户在中间阶段检查和修改结果。


### 用户确认后再持久化

正文生成完成并不等于剧情已经正式发生。

MyWriting 会先停在确认阶段。用户可以：

* 采用当前结果；
* 要求局部修改；
* 重新生成当前阶段；
* 调整剧情后继续。

只有被确认采用的结果才会进入正式状态。

因此，“模型生成了什么”和“故事世界中实际发生了什么”被明确区分开来。

### 人物档案与持续状态分离

项目将人物信息拆分为两类：

**稳定人物档案**

保存相对长期、不应频繁变化的信息，例如人物的基本设定、性格和长期关系。

**持续人物状态**

保存随着剧情推进而变化的信息，例如当前身体状态、关系变化、持有物、重要经历以及其他需要在后续剧情中继续保持的信息。

采用新的剧情后，工作流可以根据正式发生的内容更新这些状态，而不需要不断修改人物的基础档案。

### 面向连续创作的上下文管理

MyWriting 不要求把整个故事和全部资料永久塞进同一个聊天上下文。

项目将不同类型的信息分别保存在：

```text
reference/   稳定参考资料
state/       当前持续状态
history/     已确认的历史记录
input/       本轮用户输入
work/        工作流中间产物
output/      最终输出
```

工作流可以在需要时读取对应的信息，使长期项目能够依赖结构化文件继续推进，而不是完全依赖模型聊天窗口中的短期记忆。

### 可追踪的 Story History

被正式采用的剧情会留下对应的历史记录。

History 用来记录已经确认发生的内容，而不是模型生成过程中的临时草稿。后续出现状态错误、剧情冲突或需要检查某次修改时，可以回溯已经提交的故事记录。

### 写入保护

MyWriting 的插件层包含针对写作流程的写入保护机制。

状态更新和正式提交被限制在预期的工作流阶段中，降低模型因为重复调用工具、错误路径或中途失败而直接破坏正式故事状态的风险。

这使生成过程中的临时文件与已经确认的故事数据保持分离。

### 本地优先与私人数据隔离

仓库本身只保存：

* 工作流；
* DSH 插件源码；
* 测试；
* 示例配置；
* 无私人信息的模板。

实际的人物卡、人物状态、正文、本机路径配置以及运行时产物默认留在本地，并通过 `.gitignore` 排除。

因此可以公开或同步工作流代码，而不需要同时公开自己的小说内容和人物资料。
